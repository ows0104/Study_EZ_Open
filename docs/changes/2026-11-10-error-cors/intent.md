# 서버 500에도 CORS 헤더

## 문제와 사용자 효과

사용자 2026-11-10: 「자유 노트 기능을 구현했는데 실제로 웹에서 띄워보니까 failed to fetch가 나와. 이거 왜 그런 걸까?」

- 운영 API에는 `/api/me/notes`가 배포됐지만 운영 DB에 `user_note` 표가 없는 것으로 보인다(운영 DB는 직접 보지 못했다).
- 로컬 격리 sqlite에서 표만 빼면 `/api/me/notes`가 500을 내고, 그 응답에는 `Access-Control-Allow-Origin`이 없다.
- 처리되지 않은 예외는 Starlette의 `ServerErrorMiddleware`(가장 바깥)가 응답하므로 `CORSMiddleware`를 지나지 않는다.
- 브라우저는 CORS 헤더 없는 응답의 내용을 화면 코드에 넘기지 않는다. 화면에는 「Failed to fetch」만 보이고 서버 오류인지 네트워크 문제인지 알 수 없다.

## 범위와 성공 기준

- 처리되지 않은 예외로 생긴 500에도, 허용된 출처에서 온 요청이면 같은 CORS 헤더가 붙는다.
- 화면은 「Failed to fetch」 대신 HTTP 500 응답을 받는다.
- 허용되지 않은 출처에는 지금처럼 헤더를 붙이지 않는다. 기존 정상 응답·4xx 응답은 그대로다.
- 예외 내용(스택·메시지)은 응답에 넣지 않는다. 로그에는 지금처럼 남는다.

## 근거·미정 사항

- 운영 `user_note` 표 생성(`init-db`)은 이 작업 범위가 아니다. 사용자가 직접 실행한다.
