# 사이트 전체 개발 흐름 최종 점검 — 2026-10-26

판정: 기본 절차는 실제로 연결되어 있다. 다만 검증 범위·설계 변경 시 근거 갱신·자동화 지시·
배포 후 결과/사건 종료 연결에 보완점이 있어 **운영까지 완결된 루프라고 선언할 단계는 아니다.**
이번은 점검과 후속 계획 작성이다. 실행 코드·자동화 설정·운영 배포를 변경하지 않았다.

## 단계별 실제 연결

| 단계 | 확인한 동작 | 남은 부분 |
|---|---|---|
| Plan | new가 작업별 intent/spec/plan/release/state를 생성 | 조사·완료 상태를 지속적으로 표시하는 공통 수명주기 |
| Design | 요구사항·수용 기준 양식, 설계 변경 시 구현 승인 무효 | 설계 변경을 기존 테스트/리뷰 무효화에도 연결 |
| Build | 계획·설계·검사 목록에 묶인 사람 승인, 미승인/미작성 문서 차단 | 에이전트가 직접 편집하는 행위 자체를 강제 차단하는 권한 시스템은 아님 |
| Test | 실제 명령/종료 코드/로그/코드 지문 기록, 실패 후 수정·재검사, 최신 실패 우선 | 영역별 입력 누락과 변경 범위에 맞춘 검사 묶음 |
| Deploy | 서버 스크립트는 ID와 승인/검사/리뷰를 확인한 뒤 클라우드 단계 진입 | 웹 push는 문서상 사전 검사, 후보 고정·실배포/사후검증 기록은 미완성 |
| Maintain | 매시간 자동화가 실제 maintenance와 feedback pull 수행, 이상 2회 후 incident/intent 생성 | 깨진 지시문, 사건 종료 기록, 기능/DB/큐/러너 관측 확대 |

Plan→Design→Build→Test→Deploy 승인 확인과, Maintain→새 intent→미승인 구현 차단을
격리 시험에서 연결했다. 실제 클라우드 배포나 실제 장애를 유발한 시험은 하지 않았다.

## 우선 보완할 발견 사항

### 1. 자동화 지시의 인코딩과 오래된 조사 상태

study-ez 설정에 U+FFFD 대체 문자가 이름 17개, 지시문 1,815개 있었다.
단순 화면 표시 문제가 아니라 UTF-8 파일과 실제 heartbeat 입력에서도 확인된다.
최근 실행은 저장소 안내를 읽고 정상 수행했지만, 기존 승인 범위·처리 규칙을 안정적으로 전달할 수 없다.
같은 자동화의 후반 지시에는 이미 P3a에서 해결한 bank coverage 조사가 여전히 미해결로 적혀 있다.
후속 조치: 기존 승인 범위를 정상 한국어로 복구하고 해결 기록 링크를 갱신한다. 스케줄/대상 채팅은 유지한다.

### 2. 검사 코드 지문이 모든 관리 영역을 포함하지 않음

scripts/development.py:16,34의 CODE_ROOTS/source_hash에 Spotter 원본과 data/timetable, uv.lock이 없다.
격리 시험에서 이 세 파일의 내용을 바꿔도 source_hash가 바뀌지 않았다.
이는 현재 리팩토링 코드 손상을 뜻하지 않지만, 해당 영역 작업의 과거 검사/승인이 잘못 유효해질 수 있다.
반대로 포함된 영역은 전역 지문 한 개이므로 러너 변경이 관련 없는 과거 서버 검사도 stale로 만든다.
실제 입력별 범위를 정의하고 공유 의존성까지 포함한 검사 근거를 묶어 정확성과 비용을 함께 개선해야 한다.

### 3. 새 설계 승인 후 예전 테스트·리뷰가 재사용됨

scripts/development.py:122,125,189,195는 검사와 리뷰를 코드 지문에만 연결한다.
수용 기준을 바꾸고 구현 승인을 새로 기록했지만 코드는 그대로인 경우, 새 검사·리뷰 없이 release가 통과했다.
계획/설계/검사 목록의 지문도 테스트·리뷰에 포함하고 검사 도중 변경을 감지해야 한다.

### 4. 릴리스 전체를 입증하는 마지막 연결

server/deploy.ps1:23은 승인 확인을 수행하지만 확인 뒤 변경 가능한 작업 트리에서 패키지를 만든다.
마지막은 실제 사후 검사 실행이 아니라 health 확인 명령 출력이다(:164).
웹은 master push 전에 사람이 gate를 실행하도록 문서화됐으며 저장소 안 자동 강제 경로는 확인되지 않았다.
원격 브랜치 보호 설정까지 이번에 검사한 것은 아니다. 따라서 서버/웹 모두 immutable 후보와
실제 배포 버전·사후 점검·복원 결과를 같은 작업 기록에 연결하는 마감이 필요하다.

### 5. 조사·복구·해결 상태가 기록상 닫히지 않음

maintenance.py:49~51은 복구 event를 출력하고 활성 incident를 지우지만 사건 폴더에
지속적인 resolved/recovered 이력을 남기지 않는다. 피드백 ledger와 change 연결도 문서/에이전트 절차다.
bank-coverage-state는 P3a에서 해결됐고 resolution.md도 이미 있다. 다만 원래 state에는
승인·검사·리뷰가 없는 조사 기록이 남고 자동화 문구도 갱신되지 않아, 문서상 해결과 기계적 상태가 다르다.
과거 기록을 덮어쓰기보다 해결한 change를 연결하고 완료 상태를 표시해야 한다.

## 실제 검사와 운영 관찰

- 기존 workflow 검사 8개 + 정상 단계 연결 검사 2개: **10개 통과**.
- 지문 누락 3개와 설계 변경 후 근거 재사용 1개: **4개 결함 재현**(pytest strict xfail).
  xfail은 해결/통과가 아니다. 위 결함을 현재 코드에서 확인했다는 뜻이다.
- 시험은 원본 scripts와 같은 바이트의 격리 사본 및 임시 기록으로 수행했다.
  시험용 승인 문자열은 운영 기록이나 실제 배포 승인이 아니다.
- 2026-10-26 13:17:50 KST에 저장된 웹/API 관측 모두 healthy.
- 기존 채팅 ‘사이트 피드백 개선 루프 만들기’의 해당 heartbeat에서 maintenance와 feedback pull
  각각 종료 코드 0, 새 변화 없음으로 알림 생략한 실행 기록을 확인했다.
- 현재 API 100% 트래픽은 studyez-api-study-retention-20261019. 리팩토링본은 운영에 배포하지 않았다.
- 로컬 HEAD e33b142, 추적 파일 변경 192개. 기존 다른 작업을 포함한 수치이며 이번 리팩토링만의 수치가 아니다.
- 웹 운영 소스 revision은 미확정. 공개 health는 로그인 후 학습 저장·DB·큐·러너 정상의 증거가 아니다.
