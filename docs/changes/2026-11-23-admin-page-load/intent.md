# 관리 페이지 로딩 속도

## 문제와 사용자 효과

사용자 요청(2026-11-23): 「관리 페이지 로딩이 너무 오래걸려. 한번에 너무 많은 것을 가져오는 것은 아닐지 생각돼. 고쳐줘.」

`/admin`은 뜰 때 다섯 요청을 한꺼번에 보낸다. 화면은 `overview`가 올 때까지 「불러오는 중…」이다.

운영 실측(2026-11-23, 같은 화면을 세 번 연속 새로 열었다. 초):

| 요청 | 1회 | 2회 | 3회 | 혼자 부를 때 |
|---|---|---|---|---|
| `overview` (화면을 막는다) | 5.1 | 8.3 | 1.0 | 0.6–0.7 |
| `prequiz-jobs` | 0.2 | 0.1 | 0.1 | 0.1–0.2 |
| `users` | 0.1 | 0.1 | 12.7 | — |
| `card-review` | 1.9 | 2.9 | 15.2 | — |
| `bank-feedback` | 11.6 | 13초 넘게 진행 중 | 20초 넘게 진행 중 | — |

`overview` 자체는 0.6초면 온다. 느린 것은 같이 뜨는 `bank-feedback`(Quiz Bank 신고 목록)이다.
이 목록은 Main-Quiz 신고마다 그 판의 원본 문서(`root_content.document`)를 통째로 읽는다.
운영 DB에서 신고가 걸린 판은 16개, 원본 합계 81.7 MB(가장 큰 것 24.3 MB, 대부분 문항 그림)다.
인스턴스 하나가 이것을 받아 풀어내는 동안 같이 온 요청이 밀린다. 화면을 떠나도 서버의 요청은
끝까지 돌기 때문에, 느려서 새로고침하면 더 느려진다(위 2·3회).

화면이 뜰 때 이 목록에서 쓰는 것은 탭 이름 옆 숫자 하나다. `card-review`도 같다.

## 범위와 성공 기준

- 관리 화면이 뜰 때는 탭 이름 옆 숫자만 읽는다. 카드 검토·신고 목록은 그 탭을 열 때 읽는다.
- 신고 목록은 Main-Quiz 원본 대신 그림을 뺀 사본(`root_content.light`)에서 문면을 읽는다.
- 탭 이름 옆 숫자, 두 탭의 내용·동작은 그대로다.
- 성공 기준: 배포 뒤 `/admin`을 열었을 때 `overview`가 혼자 부를 때 수준(1초 안팎)으로 오고,
  화면이 뜰 때 `bank-feedback`·`card-review` 목록 요청이 나가지 않는다.

범위 밖: `overview` 응답 자체의 축소(혼자 0.6초라 이번 원인이 아니다), 카드 검토 목록의
편별 질의 묶기, DB·스키마·프롬프트.

## 근거·미정 사항

- 실측: 운영 사이트 `/admin`의 브라우저 Resource Timing. DB 크기: 운영 DB 읽기 전용 조회
  (건수와 `octet_length`만. 내용은 읽지 않았다).
- 신고가 걸린 16판의 사본 칸 합계는 14.3 MB이고 빈 행은 없다.
- 앞선 같은 종류의 수정: #73(2026-11-10, overview에서 은행 수정 이력 빼기 20 MB → 0.89 MB).
- 미정 없음.
