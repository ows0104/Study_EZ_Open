# Main-Quiz 새 출제 구조 root-generation/3 — 설계

배경과 근거는 [intent.md](intent.md)에 있다. 조사 기준은 master cb0f7e5b(2026-11-10)이며, 여기에는 `medical-final/1`과 map-tree/1 러너가 들어 있다.

## 한 장 요약

```
0 준비(코드)
1 독립 추출 ─┬ 1a 지도 /3            (map-tree/1 앞 단계 그대로)
             ├ 1b 포인트 /3 + 점검·보완 ≤1 (그대로; 남은 지적은 표시)
             └ 1c 문제은행            (원본만 보고 출제; 웹 출제본도 여기로)
  정리: 지도+포인트 → 목표(brief), 중요도 등급(코드)          (그대로)
2 커버 확인(새 프롬프트)   목표 × 문항 발문·정답 → 목표마다 커버 문항
3 빈 목표만 추가 출제 → 좁힌 커버 확인   ≤2회, 남으면 「준비 안 됨」
4 문항 검토·보완(묶음)     코드 형식 검사 → 묶음 검토 → 지적 문항만 고침 → 고친 것만 재검토
5 의학 검토               medical-final/1 그대로(끝에 한 번)
6 조립·결과 검증           문서 형식은 /2와 같다
```

## 원칙 (모든 단계에 적용)

**P1. 더하기만 하고 고쳐 쓰지 않는다.** 단계 출력 스키마에 그 단계가 바꿀 수 있는 것만 둔다.
- 3단계 출력에는 새 문항만 있다. 기존 문항과 지도는 출력에 들어갈 자리가 없다.
- 4단계 출력에는 지적받은 문항 ID의 교체본만 있다.
- 코드는 출력을 합칠 때 다음을 확인하고, 어긋나면 그 출력을 받지 않는다.
  - ID가 그 단계에 허락된 것인지
  - 기존 문항의 해시가 같은지
  - 지도 해시가 같은지

**P2. 한 번 판정한 것은 다시 판정하지 않는다.** 판정 장부 `verdicts.json`에 아래를 적는다. 문항 글(`question_hash`)이 같으면 판정을 재사용하고, 다시 묻지 않는다.

| 기록 | 내용 |
|---|---|
| 커버 판정 | (목표, 문항 해시) → 커버 판정 |
| 문항 판정 | 문항 해시 → 판정 |

**P3. 필요한 것만 넘긴다.** 단계마다 넘기는 칸을 아래 「입력 계약」 표로 고정하고, 검사가 칸 이름을 확인한다.
- 정리 이후에는 원본 지도(`conceptMap` 텍스트)와 원본 포인트(`points` 텍스트)를 넘기지 않는다. brief에 이미 들어 있다.
- 이전 판 사본(`previousAuthoring`)은 넘기지 않는다.
- 원본 대조 결과 전체(`sourceAudit`)도 넘기지 않는다.
- 원본 쪽 그림은 그 호출에 든 문항·목표가 인용한 쪽만 붙인다. 문항 자극 그림은 그 문항 것만 붙인다.

**P4. 판정 하나에는 한 가지 일만 시킨다.** 커버는 커버 확인만 본다. 문항의 원본 일치·설계는 문항 검토만, 의학은 의학 검토만 본다.
- 지금 /2의 원본 대조 한 번은 다음을 모두 함께 한다: 커버, 설계, 원본 일치, 중요도 근거, 관계, 임상 정리.
- 그래서 문항 하나가 doubt를 받으면 그 문항이 커버하는 목표까지 unknown이 됐다. 좁힌 재확인의 unknown 23개 중 15개가 이 경우다.
- /3에서는 커버 판정이 문항 판정에 묶이지 않는다.

**P5. 상한은 단계마다 정하고 재실행으로 초기화하지 않는다.** 재개(stage-resume)는 /2와 같은 규칙을 따른다. 완료 단계는 살리고, 라운드 번호는 고정하며, 자동 재시도는 없다.

## 요구사항과 수용 기준

### R0. 준비·1단계 독립 추출
- 1a·1b와 정리는 map-tree/1 앞 단계(`runner/root_front.py`)와 /2 `normalize`를 그대로 쓴다.
- 1b 점검 뒤에도 지적이 남으면 멈추지 않는다.
  - 남은 지적의 `point_ids`를 brief 포인트에 표시(`auditOpen`)하고, 결과 문서의 목표에도 보이게 한다.
  - 수용 기준: 사슬알균에서 final-audit에 남은 지적 6개가 해당 목표에 표시돼 있다.
- 1c 문제은행
  - CLI는 `parallel-source-authoring/1`의 bank 작업(`quizbank/connection_parallel.py`)을 1a·1b와 동시에 돌린다. 웹 출제본이면 그 응답을 그대로 쓴다.
  - 1c는 지도와 포인트를 보지 않는다.
  - 수용 기준: 1c 입력에 `conceptMap`·`points`·`brief`가 없다. 코드가 1c 결과의 문항 내용을 바꾸지 않는다(`preserved_bank`와 같은 투영 비교).
- 합치기는 코드가 한다.
  - 1c 문항의 `concept_id`·`point_ids`는 2단계 커버 결과에서 정한다. 커버한 목표의 개념과 포인트를 쓴다.
  - 어떤 목표도 커버하지 않는 문항은 「목표 밖 문항」으로 남긴다(미정 U1).

### R2. 커버 확인 `coverage-v3`
- 입력: 아래 「입력 계약」 C2.
- 출력: 목표마다 한 줄이다.
  - `direction_id`
  - `status`: covered · missing · unknown
  - `question_ids`: 그 목표 전체를 답으로 묻는 문항들
  - `components`: 구성 요소 → 문항의 답 단위 위치
  - `reason`
- 문항 판정과 중요도·관계 판정은 출력에 없다.
- unknown은 3단계에서 빈 목표로 센다. 문항을 하나 더 쓰는 비용이 목표를 비워 두는 비용보다 작다.
- 목표가 많으면 묶음으로 나눈다. 묶음 크기는 plan에서 실측으로 정한다.
- 판정 포기 검사
  - 한 묶음의 목표가 전부 unknown이면 판정하지 않은 검토로 본다.
  - 같은 입력으로 한 번만 새 세션에서 다시 돌린다(review-retry/1과 같은 규칙). 두 번째도 그러면 멈추고 보존한다.
  - 시험의 149문항 전체 재확인이 이 경우였다.
- 수용 기준
  - 문항 하나의 doubt가 커버 판정을 바꾸지 않는다(가짜 모델 검사).
  - 입력에 문항 해설·선지 해설·원본 쪽 그림이 없다. 자극 그림이 있는 문항은 그 그림만 붙는다.

### R3. 빈 목표만 추가 출제 `add-v3` → 좁힌 커버 확인
- 입력: 「입력 계약」 C3.
- 지적 문구는 코드가 목표 칸(cue·answer_scope·components)으로 만든다.
  - 지도를 고치라는 권고(recall_units 정의 등)는 넣지 않는다.
  - 시험에서 모델은 그 권고를 따라 목표 8개의 지도를 고쳤다.
- 출력 스키마: 새 문항(`questions`), 새 문항의 `visual_stimuli`, 새 `clinical_conflicts`뿐이다.
  - 새 ID는 코드가 정해 준 범위 안이어야 한다.
  - 코드가 기존 문제은행 뒤에 붙인다.
- 좁힌 커버 확인: 이번 빈 목표 × 이번 새 문항만 C2 형식으로 판정한다.
- 상한: 추가 출제 + 좁힌 확인을 2회까지 한다.
  - 그 뒤에도 비어 있는 목표는 「준비 안 됨」으로 결과에 남긴다.
  - 몇 회 했는지는 ledger에 적고 재개로 초기화하지 않는다.
- 수용 기준
  - 기존 문항 해시와 지도 해시가 3단계 전후에 같다.
  - 허락되지 않은 ID나 기존 ID를 출력하면 거절한다(가짜 모델 검사).

### R4. 문항 검토·보완
1. **코드 검사** — 모든 문항을 한 번 검사한다. 판정에 모델을 쓰지 않는다.
   - `validate_bank` 형식 오류: 4단계 보완 대상으로 넣는다.
   - `quality_errors` 품질 측정: 정답 노출 등이다.
   - 학생 문장 속 내부 ID(`internal_id_mentions`)
2. **묶음 검토 `item-review-v3`**
   - 문항을 개념 순서로 묶는다. 묶음 크기는 plan에서 정하고, 30~50문항으로 시작한다.
   - 입력은 C4다. 출력은 문항마다 판정 하나다.
     - `verdict`: ok · doubt · wrong
     - `checks`: 원본 일치 · 설계
     - `note`, `fix`
   - 커버·중요도·관계·임상 정리 판정은 하지 않는다.
   - 판정 장부에 해시가 같은 판정이 있으면 그 문항은 묶음에서 뺀다.
3. **보완 `fix-v3`**
   - 대상: wrong, doubt, 코드 검사 지적, 의학 판정 답 고치기(R5)
   - 입력: C5. 출력: 그 ID들의 교체본뿐이다.
   - 코드 확인
     - 대상 밖 ID는 거절한다.
     - 문항 ID와 `concept_id`·`point_ids`를 유지해야 한다.
     - 그 문항이 커버하던 목표 목록을 함께 기록한다.
4. **고친 문항만 재검토**
   - 판정이 나빠졌으면(ok→doubt/wrong, doubt→wrong) 직전 판으로 되돌린다.
   - 고친 문항이 목표를 커버하던 문항이면, 그 목표만 C2 형식으로 다시 확인한다.
5. **상한**
   - 문항마다 고치기는 2번까지다. 그 뒤 남은 지적은 결과의 문항 검토 기록에 보인다.
   - 묶음 단위 라운드 수는 ledger에 적고 재개로 초기화하지 않는다.
6. **수용 기준**
   - 지적 없는 문항 변경은 거절한다.
   - 판정이 나빠진 변경은 되돌린다.
   - 해시가 같은 문항은 재검토 입력에 들어가지 않는다(가짜 모델 검사).
   - 시험에서 좁힌 재확인이 잡은 설계 wrong 5개(Q128·Q134·Q138·Q145·Q147)와 같은 종류가 이 단계 대상이 된다.

### R5. 의학 검토
- `medical-final/1`(`MEDICAL_FINAL_PROMPT`, 입력 `medical_input`)을 그대로 쓴다.
  - 원본끼리 충돌은 판정한다. 그 밖은 "현재 의학:" 해설만 붙인다.
  - 과제에서 문항을 빼지 않는다.
- 답 고치기(사용자 「답도 고치기」): 원본 충돌 판정이 현재 답과 다르면 그 문항만 R4 보완에 넣는다.
  - 고친 뒤에는 그 문항만 의학 검토를 다시 한다.
  - 상한은 R4의 문항별 2번을 같이 쓴다.
- 수용 기준: medical-final/1 검사 6개와 같은 내용을 /3에서도 통과한다.

### R6. 조립·결과 검증
- 결과 문서(`document`)의 형식과 학생 화면은 /2와 같다. 서버 과제 선별·풀이 경로를 바꾸지 않는다.
- `manifest`에 다음을 적는다.
  - `pipelineVersion: root-generation/3`
  - 단계별 ledger, 판정 장부 해시
  - 3단계 횟수, 「준비 안 됨」 목표, 「목표 밖 문항」
- `validate_result`(studyez_contracts)에 /3 갈래를 더한다. /2 갈래는 그대로 둔다.
- 수용 기준: /3 결과를 서버 검증이 받는다. /2 결과·재개 검사가 모두 그대로 통과한다.

## 책임·입출력 계약·오류 상태

### 입력 계약

| 단계 | 넘기는 것 | 넘기지 않는 것 |
|---|---|---|
| C1c 문제은행 | 원본 글·쪽 그림, scope | 지도, 포인트, brief |
| C2 커버 확인 | 목표(`direction_id`, cue, answer_scope, components, 관계 문장)<br>문항(`question_id`, 발문, 정답, answer_units, 선지·정답 선지)<br>자극 문항의 자극 그림 | 해설, 선지 해설, 원본 쪽, 중요도, 이전 판정 |
| C3 추가 출제 | 빈 목표와 그 근거 쪽(글+그림)<br>기존 문항 발문·정답 목록(중복 방지)<br>허락된 새 ID 범위, 해당 개념·포인트 | 기존 문항 전체 칸, 원본 대조 결과, 이전 판, 원본 지도·포인트 텍스트 |
| C4 묶음 검토 | 묶음 문항 전체 칸<br>그 문항들이 인용한 쪽(글+그림)과 자극 그림<br>참조한 clinical_conflicts | 다른 문항, 목표 커버, 중요도 |
| C5 보완 | 대상 문항 전체 칸과 그 지적<br>인용 쪽(글+그림), 그 문항이 커버하던 목표 | 대상 밖 문항, 전체 검토 결과 |
| C6 의학 | `medical_input`(현행) | — |

- 쪽 그림은 `source_refs`와 목표 `evidence`의 물리 쪽으로 고른다. 인용이 없으면 그 원본의 글자만 넘긴다(미정 U3).
- 검사는 단계 입력의 최상위 칸 이름이 이 표와 같은지 확인한다.

### 오류 상태
- 다음은 그 출력을 받지 않고 단계를 실패로 기록한다. 자동 재시도는 없고 재개로 이어 간다.
  - 스키마 위반, 허락 밖 ID, 기존 해시 변경
  - 판정 포기(묶음 전부 unknown)는 위 R2의 한 번 재실행 뒤에 실패로 기록한다.
- 3단계·4단계 상한에 닿는 것은 실패가 아니다. 결과에 「준비 안 됨」과 남은 지적으로 남는다.
- 콘텐츠 거절(OpenAI 제한)은 /2와 같은 보류 처리를 한다(`remember_restriction`).

## 호환성과 데이터 보존
- **/2 보존**: /2(`connection_generate_v2.py`)와 그 ledger·재개·결과 검증은 바꾸지 않는다.
  - /3은 새 모듈(예: `quizbank/connection_generate_v3.py`)과 새 ledger 판 값을 쓴다.
  - /2 실행 폴더를 /3으로 재개하지 않는다.
- **요청 경로**: 관리자 버튼에 새 pipeline 값(예: `map-tree/2` = map-tree 앞 단계 + /3)을 더한다.
  - map-tree/1의 동작과 이어 하기는 그대로 둔다.
  - 기본값을 바꿀지는 사슬알균 시범 뒤에 정한다.
- **러너**: 새 코드를 쓰려면 러너 설치본을 다시 깔고 다시 띄워야 한다. 그 전의 러너는 모르는 pipeline을 모델 호출 전에 거절한다(map-tree/1과 같은 방식).
- **데이터**: DB 스키마는 바꾸지 않는다. 결과는 기존 `root_generation`·`RootContent` 칸에 들어간다.
  - 이미 공개된 판(감염병리1, 사슬알균 map-tree-26110901)은 그대로 둔다. 교체는 따로 묻는다.
- **기록 보존**: runs의 실행 기록(입력·원출력·사용량·실패)은 /2처럼 보존한다. 판정 장부도 실행 폴더에 남긴다.

## 미정 (plan에서 정하거나 시범으로 확인)
