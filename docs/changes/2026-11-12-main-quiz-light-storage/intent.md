# Main-Quiz 저장 방식: 그림 뺀 사본 칸·그림 표

## 문제와 사용자 효과
사용자(2026-11-12): 「다른 것보다 숫자칸이 안채워지는게 문제였어.」 → 「잠만 근데 문제를 왜 읽지? 특히 그림. 메타데이터
같은 것만 읽으면 되는거 아니야?」 → 「어 그리고 저장 방식을 바꾸는게 좋으려나?」 → 두 단계 제안에 「Both steps」.

Main-Quiz 한 판은 `root_content.document`(`json` 칸) 하나에 6–12 MB로 들어 있고 대부분이 문항 그림 base64다.
- 강의 목록·캘린더 학습률은 그림이 필요 없는데 원본을 통째로 읽었다(인스턴스 메모리 사본은 배포마다 사라짐, 6.5–8.8 s).
- 풀이 클릭(답 보기·평가)도 매번 원본을 읽었다(운영 2026-11-12: 186건, 중앙값 0.42 s, 최대 2.3 s).
- 동시에 원본을 읽다 512 MiB를 넘겨 인스턴스가 죽었다(같은 날 9번) → 숫자 칸이 끝내 비었다.
- `json` 칸은 일부만 꺼내도 DB가 글 전체를 해석한다(SQL로 그림만 빼도 문서당 0.4 s) — 읽는 쪽 손질로는 안 풀린다.

## 범위와 성공 기준
- 원본 `document`는 그대로 둔다(검수·공개된 기록). 옆에 둘을 더한다.
  1. `root_content.light`: 그림 바이트만 뺀 사본 + 원본(그림 포함)으로 계산한 문항 지문.
  2. `root_image`: 그림 바이트, 키는 PNG의 sha256(계약이 검증하는 값). 판이 바뀌어도 같은 그림은 한 줄.
- 새 판은 넣을 때 자동으로 둘을 채운다(등록 경로 다섯 곳 전부, 모델의 before_insert).
- 이미 있는 판(운영 34개)은 `python -m app.cli main-quiz-light --apply`로 한 번 채운다.
- 목록·캘린더·개요·풀이·입장은 사본만 읽는다. 그림은 화면에 띄우는 문항(또는 개인 수정·제보가 비교·보관하는 문항) 하나만 되붙인다.
- 성공: 학습자 경로에서 원본 읽기 0회. 화면에 나가는 문항·그림, 개인 수정 revision, 평가 이벤트의 문항 지문이 예전과 같은 값.

## 근거·미정 사항
- 운영 읽기 전용 리허설(2026-11-12): 34판 전부 사본+그림으로 원본 문항을 그대로 되살림(불일치 0), 지문 일치.
  원본 178.9 MB → 사본 20.3 MB, 서로 다른 그림 319개 116.1 MB. DB 620.5 MB → 약 757 MB(무료 한도 500 MB를 이미 넘어 쓰는 요금제).
- 원본 형식(계약)은 바꾸지 않는다 — 러너·계약·관리자 화면·내보내기는 그대로.
- #134(시작 때 미리 만들기·원본 한 번에 하나) 위에 쌓았다. 이제 미리 만들기는 사본 칸만 읽어 싸다.
