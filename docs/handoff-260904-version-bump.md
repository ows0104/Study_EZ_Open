# 인계 — 필기본이 새 판으로 갈렸을 때

**이 문서는 계획이다. 코드는 아직 없다.** 관리자 판단(2026-09-03)에 따라 자리만 적어 뒀고,
새 세션이 여기서 시작한다.

증분 교체(바뀐 부분만 카드를 갈아 끼우기)는 별도 문서에 있다 —
[handoff-260903-incremental-cards.md](handoff-260903-incremental-cards.md).
**그쪽은 이 문서가 고쳐진 위에 선다.** 지금은 새 판이 왔다는 것을 시스템이 제대로
알아보지 못하므로, 증분 코드를 만들어도 **불리지 않는다.**

## 이 일이 드문 일이 아니다

2026-09-03 하루에 판 갱신이 **네 건** 있었다.

    260901_03  사상충증          v1 → v2   24MB → 44MB (필기가 거의 두 배)
    260902_02  폐흡충증·장흡충증   v1 → v2   v1 은 폴더에서 사라졌다
    260903_05  실습3 흡충류       v1 → v2   v1·v2 둘 다 54쪽 — 슬라이드는 그대로, 필기만
    260903_01  장내 조충증        v1 → v2   **덱을 다 만든 뒤(18:13)에 도착했다(23:21)**

마지막 것이 특히 중요하다. **원본은 빌드 도중에도, 빌드 뒤에도 갈린다.**

## 확인된 구멍 셋

### ① 밤 쓸기가 `--force` 를 안 넘긴다

`WorkItem.reason`(`new` | `newer_version`)을 읽는 곳이 저장소에 하나뿐이다 —
`studyez/runner.py` 에서 「v2 갱신」이라고 **화면에 찍는 줄**이다. 열한 줄 뒤
`watch.build(queue, ...)` 는 `extra` 를 아예 안 받는다. 그런데 `pdf2anki.run` 은
산출물이 있는 단계를 전부 건너뛴다(`runbase.step`).

갱신된 편의 run 폴더에는 `prep.json` 부터 `.apkg` 까지 다 있다. 그러니 **아무것도
안 만들고 `source.json` 에만 새 판이 찍힌다.**

다른 두 길은 이미 막혀 있다.

    사람이 손으로   runner.run_watch_one — 덱이 있으면 멈추고 `--force` 를 안내한다
    예습            prequeue.build_one  — occupancy == NEWER 면 `--force` 를 붙인다
    복습 쓸기        뚫려 있다

### ② 문지기와 쓸기가 서로 다른 파일을 본다 — 그래서 갇힌다

    문지기  publish._owns → deck.source_pdf → run.config.json  (빌드가 쓴 것)
    쓸기    watch._already_built           → source.json       (빌드 뒤에 찍는 것)

①이 일어나면 `source.json` 만 v2 가 되고 `run.config.json` 은 v1 그대로다. 그러면

    쓸기   「이미 v2 로 만듦」 → 다시 안 집는다
    문지기 「산출물은 v1 인데 필기는 v2 다」 → 덱을 안 내보낸다

**그 편이 영원히 갇힌다.** 사람이 `--force` 로 부르기 전에는 안 풀린다.
(이 문서의 앞선 판은 「옛 덱이 나간다」고 적고 있었다. 틀렸다 — 아예 안 나간다.)

### ③ 판 번호가 같으면 내용이 갈려도 아무도 못 본다

둘 다 **파일명의 `vN` 만** 비교한다. 2026-09-04 에 `260903_03` 이 그랬다.

    16:37:24   5,769,068 bytes   ← 이것으로 18:13 에 덱을 만들었다
    19:52:03   5,791,054 bytes   ← 이름은 `..._선하은v1.pdf` 그대로

그 덱이 문지기를 **그냥 지났다.** `source.json` 은 `size` 와 `mtime` 을 적어 두는데
(`watch._source_record`) 쓸기도 문지기도 안 본다.

### 문지기 자체는 일한다

판 번호가 갈릴 때는 제대로 잡는다. `260903_01` 의 v2 가 23:21 에 도착했고, 18:13 에
v1 으로 만든 덱을 문지기가 붙잡았다. **②만 고치면 이 안전망이 산다.**

## 고치는 순서

### 0. 밀린 것을 먼저 손으로 (코드 손대기 전)

    260903_01  장내 조충증        v2 로 · 99장짜리
    260901_03  사상충증           v2 로 · 제일 크게 갈렸다
    260902_02  폐흡충증·장흡충증    v2 로

    python -m studyez watch 기생충학 --run-id <편> --build --force

셋 다 `source.json` 이 아직 v1 이라 **지금은 안 갇혀 있다.** 러너를 먼저 띄우면
①→② 로 갇히므로, **이 셋이 끝날 때까지 `studyez agent` 를 내려 둔다.**
약 1.5시간 · $40. (2026-09-04 02:00 현재 러너는 내려가 있다.)

`260903_03` 은 판 번호가 같아 문지기가 못 잡는다. 내용 차이가 22KB 분량인데
다시 만들지는 관리자가 정한다.

### 1. 지문 하나로 모은다 — ②와 ③이 같이 풀린다

지금 두 곳이 **다른 파일의 다른 값**을 본다. 한 값을 정하고 둘 다 그것을 보게 한다.

빌드가 시작할 때 원본의 **내용 해시**를 떠서 `run.config.json` 에 박고, 쓸기와
문지기가 그 해시를 현재 파일의 해시와 댄다. 그러면

    ③  이름이 같아도 내용이 갈리면 잡힌다
    ②  두 곳이 같은 값을 보므로 「끝났다 / 못 내보낸다」로 갈릴 수 없다
        빌드 도중에 갈린 것도 잡힌다 (260903_01 이 그랬다)

**`mtime` 으로 판정하지 마라.** `260901_01` 의 `v1` 파일이 `v3` 보다 **나중에** 쓰여
있다(23:11 vs 20:19). Synology 가 파일만 다시 쓴 것으로 보인다 — mtime 을 믿으면
안 바뀐 것을 바뀌었다고 본다. `size` 도 약하다(같은 크기로 갈릴 수 있다).
11MB PDF 의 해시는 수십 ms 라 비싸지 않다.

판 번호(`vN`)는 **버리지 말고 같이 둔다.** 사람이 읽는 값이고, 지금 문지기 메시지가
그 값으로 말한다.

### 2. 쓸기가 `--force` 를 넘기게 한다

예습과 같은 모양이다(`prequeue.build_one`). `reason == "newer_version"` 이면
`extra` 에 `--force` 를 실어 `watch.build` 로 넘긴다.

**비용을 먼저 보여라.** 밤에 한 편이 통째로 다시 돌면 30분 · $12~18 이다. 지금
`--max` 기본이 2 이므로 하루 최대 두 편이지만, 갱신이 하루 네 건 온 날이 이미 있다.

### 3. 시험

`tests/` 에 붙인다. 최소한 이 셋:

- 판이 갈린 run 을 쓸기가 집고, 그 빌드에 `--force` 가 실린다
- 이름이 같은데 내용이 갈린 run 을 쓸기와 문지기가 둘 다 잡는다
- `source.json` 만 새 판이고 `run.config.json` 은 옛 판인 run 이 **갇히지 않는다**
  (②의 회귀 시험)

## 하지 말 것

- **`mtime` 이나 `size` 만으로 판정하기.** `260901_01` 이 mtime 반례다.
- **쪽수가 같으면 안 바뀐 것으로 보기.** `260903_05` 가 v1·v2 둘 다 54쪽이다.
- **기록을 산출물보다 먼저 갱신하기.** `source.json` 이 앞서면 그 편이 갇힌다.
  이것이 ②의 정체다.
- **밀린 셋을 처리하기 전에 러너 띄우기.**
