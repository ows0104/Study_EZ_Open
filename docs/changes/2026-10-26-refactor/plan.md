**P0~P2: 운영 기준점 확인, 읽기 범위 정리, 공용 검증 계약·프롬프트 소유권 분리.** 기존 서비스 동작을 유지하는 로컬 구현과 검사까지다. 운영 배포, 강의 재출제, 학습 정책 변경, 운영 DB 변경, 실제 자료 이동·삭제는 포함하지 않는다.

## P0. 기준점과 활성 경로 확정

- `Study_EZ_Open`의 Git 작업 트리 상태·현재 변경·운영 배포 revision·러너 실행 사본을 각각 확인한다. 조사 중 Git status가 실패했으므로 clean으로 가정하지 않는다.
- 운영 코드와 로컬 루트가 다르면 차이를 기록하고 실제 작업 기준을 정한다. 다른 작업의 변경을 임의로 되돌리거나 섞지 않는다.
- 현재 작업/예약 작업/피드백 루프의 실행 경로와 데이터 경로를 확인한다.
- 기존 로컬 테스트 환경·테스트 명령을 확인하고 영향 범위의 기준 결과를 저장한다. 운영 `.env`를 테스트용으로 사용하지 않는다.
- 보관 후보는 목록만 만든다. 삭제·이동 명령은 실행하지 않는다.

산출물: baseline 기록, 활성 의존성 지도, 보관 후보 manifest 초안, 테스트 기준 결과.

완료 조건: 변경 기준·운영 사용 경로·기존 실패가 구분됨. 복원 기준을 만들지 못하면 파일 이동 단계로 넘어가지 않음.

## P1. 작업별 읽기 범위 정리

- 대상: `CLAUDE.md`, `docs/map.md`, `docs/architecture.md`, `docs/deployment.md`, `.ignore`, 기능별 안내.
- 공통 규칙을 짧게 유지하고 활성 제약은 색인으로, 강의별 이력은 과업 문서로 연결한다.
- README와 architecture의 생성/공개 흐름 설명 차이를 실제 코드와 대조해 정정한다.
- 기본 검색에서 work/tmp/생성물/과거 기록을 제외한다. 명시적 경로로는 확인할 수 있게 한다.
- 작업별 intent/spec/plan 및 test-results/release/incident의 짧은 양식을 마련한다.

검사: 문서 링크, 활성 지시 누락 비교, 검색 결과에 과거 release 사본이 섞이지 않는지, 대표 과제의 시작 파일 찾기.

완료 조건: 사이트/출제/연결부의 시작 파일과 검사 명령이 바로 드러나고 현재 유효한 예외를 잃지 않음.

복원: 문서·검색 설정 변경만 되돌림. 데이터·동작은 바뀌지 않음.

## P2. 공용 계약과 출제 자산 분리

### P2a. 계약

- 대상: `server/app/bank_validation/`, `quizbank/schema.py`, `quizbank/validate.py`, 실제 해당 모듈을 참조하는 생성기·러너 코드.
- DB·FastAPI·설정 의존성 없는 공유 검증을 식별한 뒤 `studyez_contracts/`로 추출한다.
- 서버와 생성기 양쪽에 필요한 기존 import 경로는 얇은 재수출로 유지한다.
- 서버 Docker 빌드 범위, Python 실행/패키지 경로, 테스트 실행 경로에 새 라이브러리가 포함되는지 확인한다. 파일만 옮기고 로컬 import 성공으로 끝내지 않는다.
- 스키마 버전과 현행 판정 의미는 유지한다. 정책 변경이 필요하면 별도 계획으로 분리한다.

### P2b. 프롬프트

- 대상: `web/src/bank/bankPrompt.md`, `lectureScopes.json`, 전달 지침 파일, `quizbank/generate.py`, `quizbank/priority_only.py`, `web/scripts/pack-extension.mjs` 및 실제 참조자.
- `content/prompts/`에 정본을 두고 읽기/패키징 경로를 갱신한다. 기존 웹 다운로드/확장 배포 동작을 보존한다.
- 변경 전후 프롬프트 텍스트·치환 결과·출제 버전·범위 지침을 비교한다. 내용이 달라지는 경우 구조 정리로 통과시키지 않는다.
- 프롬프트 패키징과 확장 ZIP 만들기의 책임을 구분한다. 웹 빌드에 필요한 아티팩트는 검증한다.

검사: 영향받는 quizbank/runner 테스트, 서버의 계약·문항 수정/게시/보존 관련 테스트, 웹 typecheck/build, 프롬프트 출력 동등성, 서버 배포 패키지 import, 기존 CLI 진입점. 외부 모델 출제나 운영 업로드 없이 수행한다.

완료 조건: 생성기가 웹 소스와 서버 전용 구현에 의존하지 않고 공용 계약·출제 자산을 통해 같은 결과를 냄. 서버와 러너의 실행 환경 모두에서 검사됨.

복원: 호환 어댑터를 유지한 상태로 변경 단위별 되돌림. 운영 배포 전까지 현재 운영 버전 유지.

## 후속 단계 — 이번 구현 승인 범위 밖

### P3. 사이트/연결부 내부 책임 분리

`server/app/routes/bank.py`를 게시·편집·피드백·학습·표현 책임으로 나누고, runner의 실행·상태·업로드 경계를 정리한다. 중복 로직은 입출력이 같은 경우만 통합한다. URL·권한·재시도·학습 기록 보존 회귀 검사를 중심으로 확인한다.

### P4. 독립 앱 정리와 실제 보관

P0의 목록을 바탕으로 정확한 원본→대상 경로, 활성 참조, 보존 이유, 복원 절차를 제시한다. Spotter는 공유 서버 의존성이 남는 한 현역 형제 앱으로 관리한다. work 사본은 실행 중/유일 수정본/운영 기준본을 제외한 뒤 복사·해시 검증·복원 시험을 거쳐 정리한다. 구형 생성 기능도 호출·기존 데이터 의존성을 확인한 후 보관한다.

### P5. 새 출제 방식 시범

사용자 상세 설명 → 새 intent/spec/plan → 승인 → 시범 강의 한 개에서 독립 추출·포인트·문항·누락 검수. 기존 points/coverage/검증 코드를 재사용할 부분을 확인한다. 기존 은행을 덮어쓰지 않는 오프라인 산출물로 비교하고 미검토·누락·비용을 평가한다.

### P6. Concept Tree 학습과 점진적 배포

Journey 정책, 현재 학습 엔진과의 차이, 개인 진행도·복습 기록의 이전 규칙을 별도 확정한다. 시범 기능으로 배포 준비 → 사람의 중요 승인 → 활성화 → 학습 동작·기록 확인. 구 엔진과 데이터로 되돌리는 경로를 확보한다.

### P7. Maintain 루프 확장

기존 피드백 루프와 중복되지 않게 API/러너/생성 작업의 기술 실패를 수집한다. 같은 사건은 빌드·강의·원인으로 묶고, 새 사건·상태 변화·사용자 판단 필요 때만 알린다. 장애 분석에서 새 intent로 연결하며 중요한 구현·배포 승인을 유지한다. 실시간/주기 감지 환경과 실제 실행 가능성을 확인한 후 활성화한다.

## 검증 명령 원칙

- 웹: `npm --prefix web run typecheck`, `npm --prefix web run build`.
- 생성기: 준비된 로컬 Python으로 `python -m pytest tests/quizbank` 또는 변경에 맞는 하위 파일.
- 러너: `python -m pytest tests/runner` 중 영향 범위.
- 서버: server 폴더에서 `.venv/Scripts/python.exe -m tests <필터>`; 파일별 독립 프로세스를 사용하는 기존 러너를 유지한다. 명시적인 격리 DB/스토리지를 확인한다.
- 큰 경계 변경 완료 시 관련 통합·회귀 검사를 넓힌다. 문서만 바꾼 단계에서 전체 출제·전체 서버 테스트를 반복하지 않는다.
- 실패는 기존 실패/새 실패/환경 문제로 구분한다. 미실행을 통과로 쓰지 않는다.
