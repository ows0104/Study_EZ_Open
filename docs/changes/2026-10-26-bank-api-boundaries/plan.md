# 구현 계획 — 승인된 후속 범위의 구체화

1. 현재 원본 작업 트리를 별도 snapshot에 복사하고 모든 대상 SHA-256을 기록한다.
2. 격리 SQLite에서 coverage 실패의 상태 차이를 기록한다. 실제 기록 손실이면 이 계획의
   테스트 기대값 수정으로 처리하지 않고 동작 수정 설계를 별도로 확정한다.
3. 원본 상태 보관·기존 평가와 숙련도·추가 문항 미평가 검사를 보강하고 coverage/retention을 실행한다.
4. 함수와 모델을 bank_api의 책임별 파일로 옮기고 기존 bank.py 호환 진입점을 유지한다.
5. mock의 참조 위치와 작업 지도·컴포넌트 가이드를 갱신한다.
   전체 검사에서 동일하게 재현된 personal_priority 기대값을 현행 내용 동일성 기준에
   맞추고 변경 내용 반례를 추가한다. bank_excluded.decisions에 load_only를 적용해
   목록 조회의 불필요한 이전 상태 칼럼 읽기를 제거한다. 운영 정책·반환값은 바꾸지 않는다.
6. 전체 서버 스크립트 검사를 파일별 독립 프로세스로 실행한다. 분리 전후 전체 OpenAPI,
   144개 경로와 권한 의존성 대조, 함수/모델 AST 동등성, 공유 계약·개발 도구 검사를 실행한다.
7. 코드 리뷰 후 원본 SHA 일치 확인·백업·해시 검증으로 승인된 파일만 원본에 반영한다.
   실제 적용 코드와 검사 snapshot 해시를 대조하고 release 준비 기록을 남긴다.

사용자의 “좋아. 후속단계 진행하자.”는 제시된 P3 후속 로컬 구조 정리와 선행 검사 해결에
적용한다. 동작·학습 정책·자료/운영 변경까지 확장하지 않는다.
복원은 work/followup-originals의 변경 전 파일과 manifest를 사용해 이 묶음만 되돌린다.
원본의 다른 미커밋 변경은 보존한다. 검증 실패는 기록하고 배포로 넘어가지 않는다.
