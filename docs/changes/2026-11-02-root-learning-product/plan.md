# 강의별 뿌리 학습 첫 제품 — 구현 계획

상태: **Implementation Plan 초안 — Spec 제안 검토 전, Build 미승인.** 제품 구현·운영 배포를 실행하지 않는다. 아래 신규 경로는 구현할 파일의 제안이며 현재 존재한다는 뜻이 아니다.

## 0. 2026-11-02 Plan 구체화 범위

사용자는 “이제 슬슬 plan 단계를 진행하려고 해”라고 요청한 뒤 “강의별 뿌리 학습 첫 제품부터 구체화”를 선택했다. 이 요청을 근거로 기존 change에서 계획을 구체화한다. 새 change를 중복 생성하거나 이 발언을 Build 승인으로 기록하지 않는다.

첫 제품의 시범 강의는 콜린성 약리학(1), `261002_01`이다. 완료할 제품 경험은 **현황 → 시작/재개 → 회상·답 확인·평가 → 다음 질문 → 오늘 변화·종료**다. 강의별 독립 지도와 오늘 추천까지 포함하되, 구현 중간에는 먼저 한 강의의 저장·재개가 되는 흐름을 연결해 검증한다. 이 중간 결과만으로 첫 제품 전체가 완성되었다고 하지 않는다.

### Plan을 확정할 때 필요한 결정

2026-11-02 추가 합의: [연결 중심 학습 기준](../2026-11-02-connection-first-design/spec.md)을 C1/C3에 적용한다. C1은 개념도·과제 연결마다 실제 시험/발문 제공/해설 등장/누락과 구조적 필요·시험·임상 근거를 구분해 검토한다. 기출 없는 필요한 뼈대도 포함 후보이며 기존 Tier 자동 변경은 하지 않는다. C3는 필요한 뼈대 선행, 중요한 연결의 반복, 범위 안 세부의 첫 학습 기회를 함께 만족하도록 정책을 구체화한다. 첫 뿌리 제품의 완료를 전체 세부 학습 완료로 표시하지 않는다. 이 추가는 문서 반영이며 저장 필드·가중치·Build 승인은 별도다.

| 결정 | 현재 합의와 검토할 제안 | 계획 확정에 필요한 결과 |
|---|---|---|
| C1. 실제 뿌리 범위 | 강의별 독립 뿌리·고유 목표 집계는 합의. 실제 목표/필수 방향과 기존 69문항의 충족 범위는 미확정 | 시범 change의 허용된 경로로 원본·트리·포인트·문항을 대조한 근거, 포함할 목표/방향/과제 목록, 미준비 목록 |
| C2. 학습 행동과 상태 | 시도+답 확인은 첫 학습, 평가 전은 미평가, 도움 없는 필수 방향 회상은 합의. 세 버튼·답만 보기·도움 충돌 처리·취소 세부는 제안 | 질문부터 평가/보류/취소까지의 상태 전이표와 사용자에게 보이는 문구. 첫 학습 정정과 자기평가 취소를 구별 |

위 세 항목을 한꺼번에 재인터뷰하지 않는다. 먼저 C1의 실제 범위와 C2의 한 과제 흐름을 제시하고, C3는 그 목표/과제 수를 사용한 예시로 검토한다. 기술적인 파일 분리·검사 구성·초점 복원은 이 계획 안에서 구체화하고, 학습 의미가 달라지는 선택은 Spec에 채택 근거를 남긴다.

2026-11-02 후속: 사용자의 “한번 해봐”에 따라 [첫 범위와 한 문제 흐름 검토안](first-learning-review.md)을 작성했다. 이어 사용자가 자료·목적지·단회 읽기 전용 대조를 명시적으로 승인하여 [콘텐츠 대조 결과](content-comparison-review.md)를 확보했다. 초기 로컬 시작 실패와 자동 승인 거절은 이 후속 승인·완료와 구별해 보존했다. C1은 원본 근거가 있는 목표 후보 15개·필수 방향 후보·기존 문항의 실제 시험 범위로 구체화했으며 최종 채택 전이다. C2는 LNK001 원문을 사용한 상태 전이·저장/재개 제안이다. 이를 콘텐츠 검수 통과나 제품 Build 승인으로 처리하지 않는다.

첫 짧은 경로 후보는 `LNK001 → Q002 → Q005 → Q047 → Q036 → Q068 → Q063 → Q060`이다. B2의 로컬 검토에 이 경로를 사용할지 검토한다. 이 8문항 완료로 다른 뿌리 목표를 완료 처리하지 않으며, 객관식은 원래 형식·선지를 유지한다. 복합 matching 과제는 목표별 평가가 준비되기 전 일괄 성공으로 연결하지 않는다. 세 분류 이름의 독립 회상 등 기존 과제가 없는 후보는 준비 전으로 남긴다. 문항 수정·추가가 필요해지면 기존 보존 정책과 별도 범위를 적용한다.

### 구현 전에 고정할 기술 산출물

- `spec.md`에 콘텐츠/학습 상태 전이, 학생/관리자 응답 필드, 세션의 콘텐츠·정책 판 고정 범위를 명시한다. 지도 열람용 응답과 풀이 중 답 단서가 제거된 위치 응답을 구별한다.
- 같은 질문에서 시도+답 확인, 평가, 보류, 취소가 가능한 순서를 정한다. 같은 요청의 재전달과 새 평가를 구별하고, 이전 콘텐츠 판·다른 사용자·오래된 세션 revision의 요청을 어떻게 거절/재동기화할지 명시한다.
- 저장 중 즉시 다음 질문을 보여주는 동작과 서버의 확정 위치를 구별한다. 새로고침 시 미확인 요청을 먼저 대조하고 저장된 확인/평가 단계로 복원하는 순서를 정한다. 서로 의존하는 쓰기는 순서대로 보낸다.
- 기능 플래그의 서버/웹 적용 위치, 기본 꺼짐, 대상 강의/사용자 범위, 비활성화 중 미확인 요청의 보관·복구 후 대조를 명시한다. 웹에서 버튼만 숨기는 것으로 접근을 제한하지 않는다.

## 1. 현재 구조에서 확인한 변경 이유

- `web/src/bank/ConceptMap.tsx`는 기존 BankConcept의 방향별 mastery/target과 progress를 보여준다. 새 첫 학습·목표 분모 계약을 그대로 충족하지 않는다.

- `web/src/bank/useStudyWrites.ts`는 메모리 큐이며 실패 시 큐를 취소한다. 영속 재전송 계약은 새로 구현해야 한다.
- 기존 `study_engine/memory.py`는 FSRS의 곡선 형태를 이용한 휴리스틱이며 완전한 FSRS가 아니다. 새 방향 상태에 자동 적용하지 않는다.
- 기존 `study_day.py`는 KST 09시 경계다. 이를 유지할지 Spec 제안에 명시했다.

## 2. 순서와 완료 산출물

### 0. Spec와 콘텐츠 기준 확정 — 현재 단계

새 Spec의 세 결정 묶음을 검토하고 기존 learner-journey의 P01~P07 중 채택 항목만 정본으로 옮긴다. 단회 CLI 대조의 목표 후보 표를 사용해 채택할 목표 분할·필수 방향·기존 과제 연결과 미준비 영역을 확정한다. 합본 족보 원본 이미지가 필요한 정답 충돌과 그림 판독은 미해결로 유지한다. 현재 에이전트가 의학 내용·정답·검수 판정을 직접 고치지 않는다. 중간 평가에서 부분 회상과 도움 받은 회상을 어떻게 표시할지도 [학습 흐름 검토안](first-learning-review.md)에서 검토한다. 검토 전 제안을 제품 기본값으로 구현하지 않는다.

### 1. 승인 후 공용 계약·콘텐츠 가져오기

- 콘텐츠 선행 작업은 [연결 검토 묶음 A](../2026-11-02-connection-first-design/plan.md)가 맡는다. `studyez_contracts/learning_links/`의 관계·방향·근거·문항 판 계약을 roots에서 가져오고 두 스키마를 중복 정의하지 않는다. 구조 검증 통과는 콘텐츠 채택/공개가 아니며 기존 draft 등록·보류·기록 보존을 유지한다. roots 계약 검사는 공용 묶음의 유효/무효/미확인 입력을 소비하는 사례를 포함한다.
- 신규 `studyez_contracts/roots/`: 판/식별자/목표/방향/출처/과제/공개 준비의 순수 검증.
- 신규 `server/app/root_learning/content.py`: 검토 묶음을 draft로 등록, 참조 은행 판·문항 지문 대조, 읽기와 활성 판 선택.
- 기존 문제은행의 raw/bank/validation·수정 차수는 쓰지 않는다. 기존 bank-response/러너 게시 경로를 호출하지 않는다.
- CLI 작성/대조 보조 도구는 시범 change의 별도 실행 범위를 적용한다. 이 제품 변경으로 무제한 검수나 새 전체 은행 생성을 승인하지 않는다.

### 2. 별도 저장·집계·추천

- 신규 `server/app/models/root_learning.py`, 모델 export, `server/app/cli.py`: 콘텐츠 판·이벤트·세션 표, 유일성 제약·RLS, 추가형 DB 준비.
- 신규 `server/app/root_learning/state.py`, `planning.py`, `policy.py`: 목표 집계·방향 평가·정책 판·오늘 추천·재계획.
- 판 이동의 동일성 연결표와 옛 이벤트 보존, 기존 개인 수정·제외를 읽는 어댑터 구현.
- 원본 이벤트·활성 판·시각을 고정하면 같은 결과를 재현할 수 있게 한다. 기존 BankState와 기존 추천 엔진의 정책은 변경하지 않는다.

### 3. API·저장 재시도·권한

- 신규 `server/app/routes/root_learning.py`, `server/app/main.py` 등록: 조회/세션/사건/취소/관리자 콘텐츠 경계.
- 신규 `web/src/types/rootLearning.ts`, `web/src/bank/useRootStudyWrites.ts`: API 타입·사용자별 영속 미확인 요청·재전달·revision 충돌 처리.
- 정답 미노출·학생 공개·타 사용자 조회/쓰기 거절, 동일 요청 중복과 다른 본문 충돌을 검사한다.

### 4. 실제 학습 화면 연결

- `StudyOverview.tsx`, `BankStart.tsx`, `BankStudy.tsx`: 기능 플래그가 켜진 준비 강의에 뿌리 현황·진입 추가. 기존 문제풀이 유지.
- 신규 `RootMap.tsx`, `RootSolve.tsx`, `RootToday.tsx`: 뼈대 탐색·현재 위치·자기평가·확정/임시 상태·오늘 변화·재개.
- 기존 `BankQuestion.tsx`, `BankSlides.tsx`의 표시 기능은 필요 부분만 재사용한다. 기존 rate 엔드포인트로 새 목표 평가를 보내지 않는다.
- 색만으로 상태를 구분하지 않고 텍스트·기호를 함께 사용한다. 키보드 평가·초점·모바일·답 노출·긴 제목·접힌 중요 미학습을 확인한다.
- `server/app/usage_actions.py`, `routes/usage.py`, `web/src/notices/GuidePage.tsx`: 서버 확인된 뿌리 시작/첫 학습/평가의 의미와 도움말 반영. 클릭을 저장 성공으로 집계하지 않는다.

### 5. Test → Review → 별도 운영 승인

격리 DB·저장소에서 아래 검사, 콜린성 한 강의 실제 콘텐츠의 수동 흐름 검토, 기존 사용자 데이터 보존 비교를 마친다. release.md에는 고정 revision·콘텐츠 판·실행 검사·남은 불확실성·마이그레이션·관측·복원을 기록한다. 승인된 고정 후보만 DB 준비 → API → 웹 → 한 강의 기능 활성화 순서로 반영한다. 운영 승인 전에는 로컬 단계에서 멈춘다.

### 실제 구현 묶음과 완료 기준

위 항목 1~5는 책임별 목록이다. 실제 구현은 다음 묶음으로 진행해 중간 결과를 확인한다. 아래 묶음은 모두 해당 intent/spec/plan에 대한 Build 승인 이후의 작업이다.

| B2. 한 강의 학습·저장·재개 — B1 이후 | `root_learning/state.py`, `routes/root_learning.py`, `app/main.py`, `web/src/types/rootLearning.ts`, `useRootStudyWrites.ts`, `RootSolve.tsx`, `StudyOverview.tsx`/`BankStudy.tsx`의 제한된 진입, API/UI 검사 | 로컬의 명시적 테스트 과제 목록으로 질문→확인→평가→다음→중단/재개를 완주. 중복 반영 없음, 실패 시 미확인 표시, 다른 계정/탭 충돌 처리. 이 목록을 오늘 추천으로 표시하지 않음 |

| B4. 오늘 추천·정책 연결 — B3 및 C3 확정 이후 | `root_learning/planning.py`, `policy.py`, 세션 생성/재개 API, 시작/오늘 화면 연결 | 준비된 과제로 유한 목록 생성. 새 진도와 급한 복습 확보, 날짜 변경 시 재계획, 진행 중 새 자료 강제 삽입 없음. 동일 입력·시각·정책 판에서 같은 추천 재현 |
| B5. 첫 제품 통합·검토 — B1~B4 이후 | 이용현황/도움말, 전체 required_checks, `release.md` | 검토된 시범 콘텐츠로 대표 여정과 실패/재개를 확인하고 기존 기능 회귀 검사. 고정 후보·관측·복원 근거 준비. 운영 활성화는 별도 중요 승인 후 |

의학 내용을 담지 않은 fixture는 저장·집계·권한 검사의 입력이며 시범 콘텐츠 검토를 대체하지 않는다. 실제 시범 콘텐츠 대조는 C1의 별도 근거를 따른다. 기존 문항 연결은 공개 상태와 개인 수정/제외를 과제 제공 시에도 확인한다. 세션 생성 후 공개 취소·문항 변경·제외가 생긴 경우의 교체/준비 문제 표시는 Spec에서 정하고 오래된 과제를 그대로 제공하지 않는다.

## 3. Test 목록과 성공 조건

아래 명령은 구현 후 실행할 계획이다. 현재 실행/통과 기록이 아니다. development.py verify로 기록하고 실제 검사 수·로그를 확인한다. 서버 검사는 각 파일에서 import 전에 격리된 임시 DB/저장소를 지정하며 server/.env를 사용하지 않는다.

| 체크 | 계획한 명령/범위 | 핵심 성공 조건 |
|---|---|---|
| root-contract | 루트 `.venv/Scripts/python.exe -m pytest tests/contracts/test_roots.py -q` | 잘못된 참조·중복 목표·미준비 필수 방향·잘못된 콘텐츠 판 거절 |
| root-state | server에서 `.venv/Scripts/python.exe -m tests root_state` | 시도/확인/평가 분리, 필수 방향 모두 충족, 같은 목표 합집합, 시간·정책 판 재현 |
| root-api | server에서 `.venv/Scripts/python.exe -m tests root_api` 및 `-m tests route_contract` | 중복/충돌/다중 탭·권한·정답 비노출·원자적 기록 |
| root-preservation | server에서 `.venv/Scripts/python.exe -m tests root_preservation` 및 study_retention·bank_personal·bank_excluded | 원래 문항·학습·개인 수정·제외 유지, 변경된 연결의 자동 승계 없음 |
| root-planning | server에서 `.venv/Scripts/python.exe -m tests root_planning` | U=0/D<=0/자료 미준비/늦은 필기/H 없음·초과/날짜 경계/유한 세션 |
| root-ui | 신규 `web/tests/root-learning.html`, `root-learning.tsx` fixture와 `root-learning.test.cjs`; 로컬 테스트 서버에서 `node --test web/tests/root-learning.test.cjs` | 실패 후 재시도·새로고침 재개·평가 즉시 이동·미확인 완료 방지·지도 왕복·모바일/키보드 |
| web-types | web에서 `npm run typecheck` | 실제 타입 검사 통과 |
| web-build | web에서 `npm run build` | 실제 빌드 성공. 자동 생성 ZIP/프롬프트 차이를 확인하고 bridge 배포 승인으로 확대하지 않음 |
| usage-actions | server에서 `.venv/Scripts/python.exe -m tests usage_actions` 및 `-m tests usage` | 저장 확인·취소·실패의 집계 의미와 사용자 격리 |

하나의 required check에 여러 명령이 필요하면 승인 후 검사 실행기를 만들고 전체 성공 여부를 단일 기록으로 묶는다. 마지막 하위 명령만으로 전체 통과를 기록하지 않는다. 실제 콘텐츠 검토는 코드 검사를 대신하지 않으며 그 반대도 마찬가지다.

`development.py verify`의 실행 위치는 저장소 루트다. 승인 후 신규 `scripts/check_root_learning.py --check <체크명>` 실행기를 만들어 각 체크를 위 표의 작업 폴더에서 실행하고 어느 하위 명령이든 실패하면 실패로 반환한다. 실행기 자체는 학습 로직을 중복 구현하지 않는다. `state.json`의 기존 9개 required_checks와 일대일로 연결하며, 최종 근거는 모든 구현을 마친 동일 revision에서 확보한다. root-ui는 실행기가 격리 서버의 시작/준비 확인/종료와 테스트 URL·출력 폴더를 관리한다. 기존 `server/tests/__main__.py`의 파일별 독립 프로세스 원칙을 유지한다.

대표 수용 예시는 다음과 같이 결과까지 비교한다. 단순 버튼 클릭 수나 프로세스 종료 코드만으로 통과시키지 않는다.

| 입력·상황 | 확인할 결과 |
|---|---|
| 한 목표, 필수 방향 2개 중 1개를 시도·답 확인 후 실패 평가 | 첫 학습 목표 1, 회상 가능 0. 다른 방향 미학습 표시. 다음 질문 진입 가능 |
| 같은 목표를 지도 두 곳에서 참조하고 과제는 여러 개 | 전체 목표와 오늘 새 목표는 각각 한 번만 집계 |
| 서버가 평가를 저장한 직후 응답이 끊겨 같은 요청을 재전달 | 평가 사건 1개와 동일한 확정 결과. 완료 화면 중복 증가 없음 |
| 평가 저장 대기 중 새로고침·계정 전환 | 원래 사용자의 미확인 요청 보존. 다른 사용자에게 표시/전송하지 않음 |
| 미준비 필수 방향 또는 선택 가능한 과제 없음 | 준비 문제를 남기고 회상 완료 불가. 분모 삭제·잘못된 오늘 완료로 숨기지 않음 |
| 자료/필수 방향 변경 또는 하루 경계 통과 | 학습 변화와 기준/시간 변화를 구별. 저장 기록 보존, 채택한 재계획 규칙 적용 |

## 4. 보존·복원·위험

- 기능 플래그는 기본 꺼짐. 미준비 강의에 기존 문제풀이가 계속 작동한다.
- 로컬/운영 전 대상 DB 스키마·활성 콘텐츠 판·사용자 상태의 복원 가능한 백업을 확보하고 읽기 복원 검사를 한다.
- 장애 시 신규 진입·쓰기를 끄고 마지막 정상 API/웹 후보로 복원한다. 새 표·콘텐츠·사용자 이벤트는 삭제하지 않는다. 미확인 클라이언트 요청도 보존하며 복구 후 동일 ID로 대조한다.
- 콘텐츠만 문제면 이전 검토된 판을 다시 활성화하되 이후 학습 사건을 지우지 않는다. 판이 다른 평가를 과거 판에 자동 적용하지 않는다.
- 기존 은행 변경이 필요해지면 이 계획에서 조용히 처리하지 않고 bank_retention과 기존 수정 상한을 적용하는 별도 범위를 제시한다.
- 주요 위험은 범위 과대 표시, 동일성 오판, 저장 성공 과장, 임시 추천 수치의 고착이다. 각각 범위 라벨·검토된 연결표·서버 확인·정책 버전/비교 시나리오로 검증한다.

## 5. 승인 범위

현재는 문서·기존 코드 조사만 수행했다. 이 초안을 승인 요청의 최종본으로 보기 전에 Spec의 주요 선택과 실제 콘텐츠 범위를 확정한다. 그 후 현재 intent/spec/plan 및 required_checks의 지문에 결부된 로컬 Build 승인을 받는다. 사용자 승인 없이 approve 명령을 실행하지 않는다. 승인된 로컬 Build가 콘텐츠 공개·운영 DB 변경·배포·crop 실행을 포함하지 않는다.
