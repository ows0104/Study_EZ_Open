# Main-Quiz 요약 빠르게(시작 때 가벼운 사본)

## 문제와 사용자 효과
사용자(2026-11-12): 「이것도 해결해줘. 다른 것보다 숫자칸이 안채워지는게 문제였어.」
(앞선 작업 2026-11-12-lecture-list-speed의 남은 것: 강의 목록 숫자 칸을 채우는 `/api/root-learning`이 6–9 s.)

근거(운영, 읽기 전용):
- `/api/root-learning` 지연: 가벼운 사본(#129) 배포 뒤에도 6.5 s·8.8 s. 오늘 배포 8번 — 사본은 인스턴스 메모리에만 있어
  배포·새 인스턴스마다 첫 요청이 공개 판 23편 원본 **103.7 MB**(최대 11.8 MB, 대부분 그림)를 다시 읽는다.
- Cloud Run 로그 「Memory limit of 512 MiB exceeded」 2026-11-12 06:04–07:45 사이 9번. 목록·캘린더·study-progress 요청이
  같은 원본을 동시에 읽다 인스턴스가 죽고(503) 사본도 같이 사라진다 → 숫자 칸이 끝내 안 채워진다.
- 사본 23편은 파이썬 메모리 43 MB(하나 1.9 MB), 만드는 동안 최고 75 MB, 줄이기 CPU 3.4 s(로컬 측정).
- SQL 안에서 그림을 빼고 읽어도 문서 하나 0.4 s(`json` 칸이라 DB가 6–12 MB 글을 매번 해석) — 근본 해법이 아니다.

## 범위와 성공 기준
- 운영 인스턴스는 요청을 받기 전에 켜진 공개 판 전부의 사본을 만든다. 배포 직후 첫 목록 요청이 원본을 읽지 않는다.
- 원본 읽기는 인스턴스 전체에서 한 번에 하나. 동시 요청은 기다렸다 같은 사본을 쓴다(메모리 초과 방지).
- 캐시 상한 32 → 64(공개 판 23편, 상한을 넘으면 매 요청 전부 다시 읽는 절벽).
- 서버 코드만. DB 스키마·데이터 변경 없음. API 응답 모양 그대로.

## 근거·미정 사항
- 사본을 DB에 저장하면(새 표/칼럼) 인스턴스 시작도 빨라지지만 운영 init-db가 필요해 사람 승인 대상이다. 이번에는 하지 않는다.
- 새 인스턴스 시작이 사본 만드는 시간(예상 5–8 s)만큼 늦어진다. Cloud Run은 준비된 뒤에 요청을 보내고, 기존 인스턴스는 keepalive 핑으로 산다.
