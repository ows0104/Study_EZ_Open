# Main-Quiz /4 옛 배치 규칙 결과의 재검증 호환

## 문제와 사용자 효과
감염과 면역 261110_03(리케차) root-generation/4 결과(`runs/_root-generation/fa71412a…`)는 2026-11-11 03:43 러너 `3b17af44`로
만들어 `auto-fa71412a…` 판으로 게시했다. 같은 날 PR #90(place-by-evidence)이 병합된 뒤 master `c4e455bb`의 공용 계약은
이 결과를 `result4: assessment is not the gathered judgments`로 거절한다.
- 서버는 `put_result`·가져오기에서만 검사하므로 지금 보이는 강의는 그대로다.
- 다시 가져오기(re-import)·재게시가 막힌다. 게시된 판을 다시 올릴 길이 없어진다.
- 원인: PR #90이 조립 규칙(`assessment_raw`의 관계 주장, `_compile`의 배치 인정)을 바꾸면서 그전에 만든 결과의 조립을 남기지 않았다.
  계약은 저장된 판정으로 조립을 다시 해 결과와 같은지 보는데, 이제 다른 규칙으로 다시 조립한다.

## 범위와 성공 기준
- 공용 계약이 /4 결과를 「현재 규칙(근거 행 배치)」 또는 「PR #90 이전 규칙(답한 부분 배치)」 중 결과가 만들어진 규칙으로 재검증한다.
  같은 결과 안에서 assessment와 audit는 같은 규칙이어야 한다.
- 생성기의 새 실행은 그대로 현재 규칙으로 만든다. 지시문·출력 형식·DB·runs/는 바꾸지 않는다.
- 성공: 리케차 결과가 master 계약을 통과하고, 옛 규칙과 새 규칙 결과가 모두 통과하며, 두 규칙을 섞은 결과는 거절된다.

## 근거·미정 사항
- 재현: `studyez_contracts.roots.automation.validate_result`가 `.runtime/main-quiz-3b17af44c4e8`에서 통과, master에서 거절(2026-11-11).
- 리케차 결과의 커버 근거 행 중 17개가 관계를 적었지만 답한 부분이 없다. 옛 규칙은 이 행을 배치에 쓰지 않았다.
- 옛 결과를 계속 검증할지는 사용자가 아직 정하지 않았다. 2026-11-11 PR #89(batchMode)가 「이전 실행은 만든 방식대로」를 택한
  선례를 따라 호환으로 구현하고, PR에서 결정을 받는다.
- 표지(marker) 방식은 택하지 않았다: `c4e455bb` 러너가 이미 설치돼 표지 없는 새 규칙 결과가 나올 수 있다.
