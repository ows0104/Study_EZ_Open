# 강의 목록 정보 먼저 보이기

## 문제와 사용자 효과
사용자(2026-11-12): 「강의 목록 페이지의 정보가 보이는게 너무 느려. 무거운 걸 미루더라도 (복습 퀴즈 연결 같은거...? 잘모르겠음) 정보를 먼저 보여주면 좋을 것 같아.」

Cloud Run 요청 기록(2026-11-12, 53f0fc92 light 사본 배포 뒤)으로 잰 강의 목록 로딩:

| 요청 | 시간 | 화면에서 하는 일 |
|---|---|---|
| `GET /api/timetable?include_study=false` | 0.1–0.3 s | 행·제목·교수·번호·Main-Quiz 열림 표시 |
| `GET /api/root-learning` | 6.5–8.8 s (배포 직후 11–20 s, 500/503 포함) | 문항 단계 수·복습 수·학습률 |
| `POST /api/timetable/study-progress` ×N (8강의씩, 3개 동시) | 첫 묶음 2.8–5.5 s, 이후 0.1–0.5 s | 행의 「—」 해제와 ▶ 켜기만 |

행은 study-progress 응답까지 흐리게(`is-closed`) 「—」와 꺼진 ▶로 기다렸다. 그런데 study-progress는 같은 강의를
`/api/root-learning`과 동시에 한 번 더 채점한다(같은 Main-Quiz 문서를 둘이 동시에 읽어 서로 늦춘다).
목록에 쓰는 숫자는 전부 `/api/root-learning`에서 온다.

## 범위와 성공 기준
- 시간표가 오면(0.1–0.3 s) 행·제목·교수·▶를 바로 그리고 ▶는 바로 누를 수 있다(Main-Quiz가 열린 강의).
- 숫자 칸만 요약을 기다리며, 기다리는 동안은 「…」(0과 다름)로 보인다. 요약이 실패하면 「—」로 멈춘다.
- 강의 목록은 study-progress를 부르지 않는다. 요약 요청은 시간표와 동시에 출발한다.
- 웹만 바꾼다. 서버·DB·API 계약 변경 없음.

## 근거·미정 사항
- `/api/root-learning` 자체(배포 직후 light 사본이 비어 있을 때 6–11 MB 문서를 강의마다 읽는 비용)는 이 작업에서 줄이지 않는다.
  서버 쪽 `routes/root_learning.py`는 다른 세션(선지 번호 키)이 고치는 중이다. 후속으로 따로 다룬다.
