## 범위와 성공 기준
이번 변경(1차)은 선지 단계만 고친다. 문항·판·계약(`root-mcq/2`)·서버·웹·학습 기록은 그대로다.

- 선지 작성 한 응답이 300초 선에 걸리지 않게 한다: 묶음 40 → 12문항, 함께 도는 묶음 3 → 8.
- 족보에서 오지 않은 오답의 `jokbo` 칸은 null로 받는다(빈 문자열 다섯 칸을 쓰게 하지 않는다).
- 순서 맞추기 판정은 선지와 나란히 돈다.
- 성공 기준: 문항 190개 안팎 강의의 선지가 10분 안에 끝나고, 한 묶음이 300초를 넘겨 다시 받는 일이 없다.
  오답 수·출처 분포·검토가 뺀 비율이 이전 판과 같은 범위다.

/4 출제 단계의 순서 재배치와 단계 삭제는 이 변경에 넣지 않는다. 삭제 후보는 실측과 함께 사용자에게 묻는다(spec 「다음」).

## 근거·미정 사항
- Codex 세션 기록(`~/.codex/sessions/2026/11/23·24`, 261123_01의 선지 묶음 9개):
  입력을 읽는 데 25~50초, 그 뒤 답 하나(1.3만~1.7만 출력 토큰)를 쓰는 동안 기록이 260~290초 조용하다.
  조용한 시간이 300초에 닿으면 `token_count`만 남기고 처음부터 다시 받는다(묶음 0: 여섯 번, 41.7분 · 묶음 7: 여섯 번, 35.8분 ·
  묶음 6: 한 번, 9.9분 · 묶음 3·4·5: 0번, 4.7~5.3분). 다시 받을 때 누적 토큰이 그대로라 앞의 시도는 버려진 것이다.
- 11-23~24 전체 호출 705건(`runs/_llm/usage`): 선지 작성 43건이 호출 시간의 22%(437분), 중앙 305초, 43건 중 25건이 290초를 넘었다.
  290초를 넘은 호출의 길이는 4~5분과 9~10분에 몰린다(한 번 다시 받은 모양).
- 같은 날 normalize 실패(job 728, `idle timeout waiting for websocket` 네 번, docs/changes/2026-11-23-stage-timeout-3600)도 같은 선이다.
  그때는 단계 시한을 늘렸다. 이번에는 응답을 작게 한다.
- 선지 작성 출력의 글자 수(묶음 여섯 개 평균 4.2만 자): 오답 글 5% · basis 5% · why_tempting 12% · why_wrong 14% ·
  `jokbo` 칸 22%(대부분 빈 문자열) · 나머지는 키·따옴표.
- 미정: 응답이 조용한 까닭(구조화 출력이 끝까지 모였다 오는지)은 CLI 밖이라 확인하지 못했다. 300초 선 자체를 늘리는 설정은
  내장 공급자에 먹는지 실제 호출로 확인해야 해서 이번에 넣지 않는다.
